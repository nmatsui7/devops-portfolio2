This is Volume 2. It assumes you have completed Volume 1 or already know Docker, Docker Compose, Kubernetes basics (Deployments, Services, Ingress), Terraform, GitHub Actions, Prometheus/Grafana, and Ansible. If any of those terms are unfamiliar, start with Volume 1 first.

1b. models.py — The Todo Database Model

This file defines what a "todo" looks like in the database. SQLAlchemy translates the Python class into a PostgreSQL table.

Open app/models.py. You will see:

app/models.py — before your editfrom flask_sqlalchemy import SQLAlchemy
from datetime import datetime, timezone

db = SQLAlchemy()

# TODO: Define the Todo model ...
Step 1: Delete the TODO comment block (everything from # TODO to the end of the file). Replace it with a class definition. Type this exactly: 
class Todo(db.Model):
    __tablename__ = "todos"

db.Model is SQLAlchemy's base class — every table model inherits from it. __tablename__ sets the database table name to "todos". The tests look for this exact name.

Step 2: Add the id column. Indented inside the class, type: 
    id = db.Column(db.Integer, primary_key=True)

db.Column defines a column. db.Integer is the type. primary_key=True makes it the auto-incrementing primary key. Every SQLAlchemy model needs at least one primary key column.

Step 3: Add the title column: 
    title = db.Column(db.String(200), nullable=False)

db.String(200) maps to PostgreSQL's VARCHAR(200). nullable=False means every todo must have a title — the database enforces this.

Step 4: Add the completed column: 
    completed = db.Column(db.Boolean, default=False)

db.Boolean maps to PostgreSQL's BOOLEAN. default=False means new todos start as not-completed. Notice this is a Python default, not a database-level DEFAULT.

Step 5: Add the created_at timestamp: 
    created_at = db.Column(db.DateTime, default=lambda: datetime.now(timezone.utc))

db.DateTime maps to TIMESTAMP WITH TIME ZONE. The default calls a function that returns the current UTC time. The lambda is important — it makes Python call datetime.now() fresh each time a new row is created, instead of evaluating it once when the class is loaded.

Step 6: Add the updated_at timestamp: 
    updated_at = db.Column(
        db.DateTime,
        default=lambda: datetime.now(timezone.utc),
        onupdate=lambda: datetime.now(timezone.utc)
    )

onupdate fires every time the row is updated. This lets you track when a todo was last modified without writing manual timestamp code in every route handler.

Step 7: Add the to_dict() method. Indented at the same level as the columns, type: 
    def to_dict(self):
        return {
            "id": self.id,
            "title": self.title,
            "completed": self.completed,
            "created_at": self.created_at.isoformat(),
            "updated_at": self.updated_at.isoformat(),
        }

This serializes the model into a Python dictionary. The .isoformat() calls convert the datetime objects into strings like "2026-06-09T12:00:00+00:00". The tests call .to_dict() on every response.

OOP concepts in this class:

class Todo(db.Model): — defines a new class, like a blueprint. The db.Model in parentheses means inheritance: Todo gets all the behavior of SQLAlchemy's Model class (saving, querying, deleting) and adds its own columns and methods.

__tablename__ = "todos" — a class variable. It belongs to the class itself, not to any particular instance. Every instance of Todo points to the same "todos" table. SQLAlchemy reads this at import time to know which database table to use.

def to_dict(self): — an instance method. The self parameter is how a method refers to the specific instance that called it. When you write todo.to_dict(), Python automatically passes the todo instance as self. You never pass self yourself — Python fills it in. Without self, methods cannot access the instance's data.

Why no __init__? — Most Python classes have an __init__ method (def __init__(self, title):) that sets attributes on self. SQLAlchemy models skip this because SQLAlchemy creates instances internally from database rows using its own initialization logic. The columns defined at the class level (id, title, etc.) are special SQLAlchemy descriptors — they look like class variables but act as instance attributes at runtime.

underscore naming: — __tablename__ is a dunder (double underscore) attribute. Python reserves names like __xxx__ for special purposes. SQLAlchemy looks for __tablename__ specifically to determine the database table name. Other tools like to_dict() use regular names because they are your own application methods.

Indentation matters. All columns and methods must be indented exactly 4 spaces inside the class. Python will raise IndentationError if the spacing is wrong. If you see that error, check your editor shows spaces, not tabs.

Your complete app/models.py should now look like:

Layer 4 — Request Hooks

Find the TODO comments for before_request and after_request. Replace them with:

app/app.py — request hooks@app.before_request
def before_request():
    request._start_time = time.time()


@app.after_request
def after_request(response):
    if hasattr(request, "_start_time"):
        latency = time.time() - request._start_time
        REQUEST_LATENCY.labels(
            method=request.method, endpoint=request.path
        ).observe(latency)
    REQUEST_COUNT.labels(
        method=request.method,
        endpoint=request.path,
        status=response.status_code,
    ).inc()
    return response

What this does:

  • before_request runs before every route handler. It stamps the start time onto the request object.
  • after_request runs after every route handler (even if it raised an exception). It calculates how long the request took, records the duration in the REQUEST_LATENCY histogram, and increments the REQUEST_COUNT counter with the HTTP method, path, and status code.
  • The if hasattr(...) guard prevents errors if before_request was somehow skipped.
Why the underscore in request._start_time?

In Python, underscores in variable names are conventions that signal intent:

PatternExample from this projectMeaning
_single_leading request._start_time, _db in tests "This is internal/private — use at your own risk." It is a convention, not enforced. You can still access it, but the underscore warns other developers it is an implementation detail that could change.
__double_leading_and_trailing__ __name__, __tablename__, __init__ "Dunder" (double underscore) methods are Python's magic hooks. __name__ holds the module name (set by Python itself). __tablename__ is read by SQLAlchemy to know the database table. __init__ is the constructor. You define these to tell Python or a library how to treat your object.
_single_standalone for _ in range(5): "I don't care about this value." A throwaway variable — you are required to unpack something but have no use for it.

request._start_time uses a single leading underscore because it is a custom attribute we attached to Flask's built-in request object. The underscore says "this is not a standard Flask attribute — we added it ourselves and it is internal to this function." Without the underscore it would still work, but the convention helps other developers reading your code distinguish between Flask's official attributes (request.method, request.path) and the ones you attached temporarily.

Order matters: before_request and after_request must be defined above the route handlers in the file. Flask processes decorators in order. If you place them below a route, that route will not trigger the hooks.

Route 5: POST /api/todos — create a todo

Replace pass in def create_todo(): with:

    with tracer.start_as_current_span("create_todo"):
        data = request.get_json()
        if not data or not data.get("title"):
            return jsonify({"error": "title is required"}), 400
        todo = Todo(title=data["title"])

Line by line:

  • request.get_json() — parses the JSON request body into a Python dict. Returns None if the body is not valid JSON.
  • if not data or not data.get("title") — validates that a title was provided. Returns HTTP 400 (Bad Request) if missing.
  • Todo(title=data["title"]) — creates a new SQLAlchemy model instance. Only title is set; completed defaults to False from the model definition.
  • db.session.add(todo) — stages the new row for insertion.
  • db.session.commit() — flushes the staged changes to PostgreSQL. Without this, the row is never persisted.
  • 201 — HTTP 201 means "Created." This signals to the client that a resource was created, as opposed to 200 which is a generic success.

Basic network concepts used in this table:

What is an endpoint?

An endpoint is a URL path (the part after the domain name) that represents a specific resource or action in the API. For example, in http://localhost:8000/health, the path /health is the endpoint. Think of it as a door: each endpoint is a different door on the same building (the server). You knock on a specific door to get a specific thing.

What are HTTP methods (GET, POST, PUT, DELETE)?

HTTP methods are verbs that tell the server what you want to do. They follow the CRUD pattern (Create, Read, Update, Delete):

MethodMeaningAnalogyUsed for...
GETRetrieve dataReading a menu — you see what is there without changing anythingListing todos, viewing one todo, health checks
POSTCreate new dataPlacing an order — you send information to create something newCreating a new todo
PUTUpdate existing dataEditing an order — you send changes to something that already existsMarking a todo as completed
DELETERemove dataCrossing an item off a list — you remove it permanentlyDeleting a todo

GET is the only method that should never change data on the server. You can refresh a GET request a hundred times and get the same result. POST, PUT, and DELETE change data.

What is the :id in /api/todos/:id?

:id is a URL parameter — a placeholder for a specific value. When a client calls GET /api/todos/3, Flask captures 3 as the todo_id variable. The colon marks it as a variable, not a literal part of the path. You never type :id literally — you replace it with an actual ID.

What do HTTP status codes mean?

Every HTTP response includes a three-digit code telling the client whether the request succeeded:

CodeNameWhat it meansUsed in this project when...
200OKSuccess — the response body contains what you asked forHealth check passes, a todo is returned or deleted
201CreatedA new resource was created successfullyA new todo is created via POST
400Bad RequestThe client sent something invalid (missing field, bad JSON)A POST has no title field
404Not FoundThe requested resource does not existGET /api/todos/999 when todo 999 does not exist
503Service UnavailableThe server is alive but cannot handle requests (a dependency like the database is down)Database connection fails in the /ready check

Codes in the 200s mean success. Codes in the 400s mean the client made a mistake. Codes in the 500s mean the server or a dependency broke.

The /ready endpoint is particularly important. Unlike Volume 1 where readiness was a static string, this endpoint actually checks the database connection — the code you wrote in Step 1c:

app/app.py — the readiness probe you wrote@app.route("/ready")
def ready():
    try:
        db.session.execute(db.text("SELECT 1"))
        return jsonify({"status": "ready", "database": "connected"}), 200
    except Exception as e:
        return jsonify({"status": "not ready", "database": str(e)}), 503
Why this matters: Kubernetes uses the readiness probe to decide whether a pod should receive traffic. If the database is down, the pod reports "not ready" and Kubernetes removes it from the service. This prevents cascading failures — requests do not pile up against a pod that cannot serve them.

The Dockerfile and compose file use Gunicorn (Green Unicorn), a production-grade WSGI server. The --workers 4 flag starts four worker processes, allowing the app to handle up to four requests concurrently. The --access-logfile - and --error-logfile - flags send logs to stdout/stderr so Docker and Loki can collect them.

4. Helm Packaging

Why Helm?

In Volume 1 you applied Kubernetes manifests with kubectl apply -f. That works for small projects but breaks down when you need:

  • Environment overlays: Different values for staging vs production (replicas, resources, URLs)
  • Template reusability: One chart deployed to many environments
  • Release management: Track what was deployed, when, and with which values
  • Rollbacks: helm rollback reverts to a previous revision

Helm packages Kubernetes YAML into charts. A chart is a directory with a standard structure.

Chart Structure

helm/portfolio-app/helm/portfolio-app/
  Chart.yaml          # Metadata: name, version, description
  values.yaml         # Default configuration values
  values-staging.yaml # Staging-specific overrides
  values-production.yaml   # Production-specific overrides
  templates/
    _helpers.tpl      # Reusable named templates
    deployment.yaml   # Deployment definition (uses {{ .Values.replicaCount }})
    service.yaml      # Service definition
    ingress.yaml      # Ingress with TLS
    hpa.yaml          # HorizontalPodAutoscaler
    pdb.yaml          # PodDisruptionBudget
    serviceaccount.yaml
    configmap.yaml
    secret.yaml
    networkpolicy.yaml
    tests/
      test-connection.yaml  # Helm test pod

The key idea is parameterization. Instead of hardcoding replica count, image tag, or resource limits, the templates use Go template syntax: 

helm/portfolio-app/templates/deployment.yaml (excerpt)spec:
  replicas: {{ .Values.replicaCount }}
  template:
    spec:
      containers:
        - image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

You deploy with different values per environment:

terminal# Deploy to staging

  --namespace staging \

  --set image.tag=v2.0.0

helm upgrade --install portfolio-app ./helm/portfolio-app \
  --namespace production \
  --values ./helm/portfolio-app/values-production.yaml \
  --set image.tag=v2.0.0

Helm best practices: Store values files in Git alongside your chart. Use --set only for values that change per deploy (like image tag or database password). Never commit secrets to values files — use Kubernetes External Secrets or Sealed Secrets.

5. GitOps with ArgoCD

Volume 1 used GitHub Actions to run kubectl set image directly. That works but has a problem: drift. If someone manually edits a deployment with kubectl edit, the cluster state diverges from what CI deployed.

GitOps solves this by making Git the single source of truth. ArgoCD continuously monitors a Git repository and synchronizes the cluster to match. If someone edits a resource directly, ArgoCD reverts it. If you merge a PR, ArgoCD applies the change automatically.

Installing ArgoCD

terminal# Create namespace
kubectl create namespace argocd

# Install ArgoCD
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# Wait for all pods to be ready
kubectl wait --for=condition=ready pod -l app.kubernetes.io/name=argocd-server -n argocd --timeout=5m

# Get the initial admin password
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d

# Port-forward to access the UI
kubectl port-forward svc/argocd-server -n argocd 8080:443

Application Definitions

ArgoCD Applications tell ArgoCD what to deploy and where. Here is the staging application:

argocd/application-staging.yamlapiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: portfolio-staging
  namespace: argocd
spec:
  project: portfolio
  source:
    repoURL: https://github.com/yourorg/devops-portfolio2.git
    targetRevision: main
    path: helm/portfolio-app
    helm:
      valueFiles:
        - values-staging.yaml
  destination:
    server: https://kubernetes.default.svc
    namespace: staging
  syncPolicy:
    automated:
      prune: true      # Delete resources removed from Git
      selfHeal: true   # Revert manual changes
Important: With selfHeal: true, ArgoCD will undo any kubectl edit or kubectl patch commands. This is the desired behavior — Git is the source of truth.

The argocd/project.yaml defines the project with allowed source repos and destination clusters:

    - namespace: staging

    - namespace: production
      server: https://kubernetes.default.svc

Before you start: This Helm chart expects PostgreSQL to be reachable at portfolio-db:5432 by default. In a local cluster, create a PostgreSQL service first or override the database settings with --set config.database.host=..., --set config.database.user=..., --set config.database.password=..., and --set config.database.name=....

Build the application image and make it available to your local cluster:

docker build -t portfolio-app:local app/

# If you use kind:
kind load docker-image portfolio-app:local

# If you use minikube:
minikube image load portfolio-app:local

Deploy the API into a local Kubernetes namespace:

kubectl create namespace portfolio --dry-run=client -o yaml | kubectl apply -f -

  --namespace portfolio \

10. Ansible over SSH with a Docker Linux Target

Volume 1 introduced Ansible with localhost and a small optional SSH practice lab. This Volume 2 lab makes the remote-server model more explicit: Docker runs three Ubuntu Linux containers with SSH and Python installed, and Ansible connects to them as if they were remote hosts.

In real operations work, you often manage several similar servers. You do not want to SSH into each one manually and repeat the same commands. Ansible lets you describe the desired configuration once, then apply it to every host in an inventory group.

The ping command is only a pre-flight check. It proves Ansible can connect to every target over SSH and run Python. The playbook is the real exercise: it turns three plain Linux containers into three small web servers. Each server receives the same base configuration, but the generated page includes host-specific facts so you can see that Ansible configured each target separately.

Local-only safety note: This lab is for learning Ansible SSH mechanics only. Do not expose these SSH containers to the internet, and do not reuse the password ansible123.

Open ansible/ssh-lab/. The lab contains:

The playbook describes the actions Ansible should perform. The template describes what the generated file should look like. Ansible fills in the Jinja2 variables separately for each worker, so the same template produces a slightly different page on worker1, worker2, and worker3.

The ansible.builtin.template module is more realistic than inline copy for generated config files. Real teams use templates for nginx config, app config files, environment files, systemd unit files, and generated status pages.

Why Python matters: Most normal Ansible modules run Python on the target machine. This lab's Docker image installs python3 during the build so the happy path works without extra setup.
